1. 그래프로부터 가능한 분석
- 핵심 허브 키워드 식별: `solar/pro/model` 같은 중심 노드
- 주제 군집 파악: 성능(`latency/throughput`), 품질(`reasoning/accuracy`), 운영(`api/deployment`)
- 브리지 키워드 탐지: 서로 다른 군집을 잇는 단어(예: `model`, `performance`)
- 중요도 변화 추적: 향후 문서들과 비교해 강조점 이동(품질 중심 → 비용/운영 중심 등)

2. 단일 원문 외에 “유사 솔루션/프로덕트 합본” 생성 가능 여부

- 같은 방식으로 각 문서에서 키워드 추출 후 통합 코퍼스(합본 wordfreq + 문서별 메타데이터) 구성하면 됩니다.

3. 합본일 때 그래프 관계를 3노드까지만 해야 하나
- 고정 제한은 아닙니다.
- 다만 실무적으로는 `2-hop~3-hop`이 해석 가능성과 노이즈 균형이 가장 좋습니다.
- 4-hop 이상은 연관성 약화/잡음 급증이 잦아 별도 필터(가중치 임계값, PMI 등)가 필요합니다.

4. 관계된 원문을 청크해서 DB화 가능 여부
- 가능합니다.
- 권장: `청크 텍스트 + 임베딩 + 키워드 노드 연결 + 출처/날짜/문서ID`를 함께 저장.
- 즉, 그래프(관계)와 VectorDB(의미검색)를 같이 쓰는 하이브리드 구조가 적합합니다.

5. 이때 핵심 문제점
- 용어 정규화: `model/models`, `llm/llms`, 한영 혼용 동의어
- 노이즈 토큰: 깨진 단어, 숫자 토큰 처리 기준
- 엣지 신뢰도: 단순 빈도만으로 관계를 만들면 허위 연관 증가
- 문서 편향: 브랜드/공지성 단어가 과대표집
- 시간 드리프트: 시점 다른 문서 합치면 관계 왜곡
- 청크 경계 문제: 문맥이 잘려 잘못된 연결 생성
- 중복 문서: 같은 내용 재게시 시 특정 관계가 과대강화됨

원하면 다음 단계로, `그래프 스키마(노드/엣지/가중치)`와 `VectorDB 메타필드`를 바로 실행 가능한 형태로 설계해드리겠습니다.

1. 역량 온톨로지(정의서)
- `역량`을 무엇으로 볼지 고정해야 합니다.
- 예: `모델서빙`, `성능튜닝`, `프롬프트설계`, `평가/벤치마크`, `MLOps`.

- 엣지를 단순 연결이 아니라 `requires / improves / uses / evaluated_by` 같은 타입으로 구분해야 합니다.

3. 원문 근거 매핑
- 각 엣지/노드가 어떤 문장(청크)에서 나왔는지 근거 링크가 있어야 추론 결과를 설명할 수 있습니다.

4. 키워드→역량 매핑 규칙
- 예: `latency, throughput, serving` → `서빙 최적화 역량`
- 규칙 기반 + 임계치(가중치/빈도/PMI) 필요.

5. 직무/과업 컨텍스트
- 같은 키워드도 목표가 다르면 요구역량이 달라집니다.
- 예: 제품기획 vs 엔지니어링 vs 영업기술.

6. 검증셋
- 사람이 라벨링한 샘플(정답지)로 추론 정확도 점검이 필요합니다.
