# 온디바이스·무료 티어 전환 계획

## 1. 목적
- 유료 클라우드 LLM/OCR API 의존을 제거하고, **온디바이스 완결 MVP**를 재정의한다.
- 기존에 갈라져 있던 **「로컬 DB 자료 확보」**와 **「OCR 인식률/매칭」**은 같은 안건이다.  
  → 단일 워크스트림 **Local Scan Core**로 병합한다.
- 서버 상시 인스턴스(VM/항상 켜둔 API)는 MVP에서 쓰지 않는 것을 전제로 한다.

## 2. 확정 제약
1. 유료 모델 API 사용 금지: `solar-pro2`, `gemini`, `gpt-4.1-mini`, `Upstage Document OCR` 등은 MVP 범위에서 제외.
2. 추론 비용: **기기 로컬 = 0원**. Cloudflare Workers AI는 무료 Neurons 한도 내 **선택 보조**만.
3. **스캔/도감 조회 핫패스는 항상 온디바이스.** 네트워크·서버 DB 없이도 동작해야 한다.
4. 상시 서버 인스턴스 없음. Dex 빌드는 개발자 PC/CI에서 배치로만 수행.
5. 앱 번들 용량 우선. 1B·PP-OCR은 옵트인 다운로드.
6. **SQLite 역할 분리 (확정):**
   - **빌드** = CI/개발 PC에서만 (`PokéAPI → dex.sqlite`). 유저 기기가 API로 대량 fetch하지 않음.
   - **기기** = 사전 빌드된 DB를 **읽기 위주**로 연다. 쓰기는 컬렉션 등 소량만.
   - 규모(텍스트 ≤15MB)에서 모바일 SQLite 부담은 실무상 문제 없음.

## 3. 목표 아키텍처

```text
[Mobile App — 핫패스, 오프라인]
  ├─ OS OCR (+옵션 PP-OCR)
  ├─ Local Dex (SQLite) + name_aliases     ← 도감 진실원
  ├─ Fuzzy Matcher                         ← OCR↔DB 동일 안건
  ├─ Answer Composer (템플릿 ± 온디바이스 1B)
  └─ Local collection (기기 내)

[빌드 타임 — 개발자/CI, 인스턴스 아님]
  └─ scripts/build_local_dex → dex.sqlite 산출

[선택 클라우드 — 콜드패스만]
  ├─ Cloudflare: Dex 스냅샷 파일 배포(R2/KV 등)
  └─ Supabase(후순위): 계정/컬렉션 동기화만. 스캔·매칭에 미사용
```

### 3.1 역할 분리
| 계층 | 역할 | 비역할 |
| --- | --- | --- |
| 로컬 Dex DB + 규칙 | 진실원. 조회/상성/진화 계산 | 장문 창작 대화 |
| Fuzzy Matcher | OCR/검색 문자열 → 후보 | 비전 분류(인형) |
| OS OCR / PP-OCR | 카드·문서 텍스트 추출 | 텍스트 없는 굿즈 인식 |
| 온디바이스 1B | 의도 분류, 단답 문장화 | GraphRAG급 장문 추론 |
| Cloudflare 무료 | Dex 파일 배포·실험 | 상시 챗/스캔 백엔드 |
| Supabase (옵션) | 로그인·기기 간 컬렉션 sync | 도감/OCR 핫패스 |

## 3.2 DB 결정: SQLite vs Supabase (동접·트랜잭션)

### 결론
| 용도 | MVP 선택 | 이유 |
| --- | --- | --- |
| 도감·alias·상성·스캔 매칭 | **기기 SQLite** | 오프라인, 비용 0, 동접=유저 수와 무관(기기당 1 DB) |
| 사용자 컬렉션/계정 동기화 | **나중에 Supabase 가능** | 핫패스 아님. 없어도 MVP 성립 |
| 상시 API 인스턴스 | **사용 안 함** | 온디바이스 전제와 충돌 |

**Supabase를 “바라봐도 되는가?”**  
- **도감/OCR용 주 DB로 바라보면 안 된다.** 스캔마다 Postgres를 치면 무료 티어·동시 접속·지연이 바로 병목이 된다.  
- **계정·컬렉션 sync용으로만 후순위에 두는 것은 괜찮다.** (기기 로컬이 source-of-truth, 클라우드는 백업/동기화)

**동접·트랜잭션이 많을 때?**  
- 스캔 핫패스: 유저 10만 명이어도 **각 폰의 SQLite**에서 읽는다 → 공유 DB 동접 문제 자체가 없다. 쓰기는 컬렉션 정도의 기기 로컬 트랜잭션이면 충분.  
- Supabase를 sync에 쓸 경우: “가끔 업로드/다운로드” 수준이면 Free/Pro로도 일반적이다.  
  **모든 스캔·모든 조회를 Supabase 트랜잭션으로 처리하는 설계는 하지 않는다.**  
- Dex 갱신: 앱이 새 `dex.sqlite` 스냅샷을 받는 **파일 교체**이지, 수천 행 온라인 UPSERT가 아니다.

### 권장 데이터 흐름
```text
PokéAPI (빌드 시 fetch)
  → CI/로컬 스크립트가 dex.sqlite 생성
  → 앱에 번들 또는 CDN/R2에서 다운로드
  → 기기에서 OCR → alias match → 결과 표시
  → (옵션) 컬렉션만 Supabase에 가끔 sync
```

## 4. OCR 권장안과 인식률

### 4.1 권장 스택 (MVP)
1. **1차 OCR:** 플랫폼 OCR
   - iOS: Apple Vision (`VNRecognizeTextRequest`)
   - Android: Google ML Kit Text Recognition (필요 시 한/일 스크립트 팩)
2. **2차 OCR(선택):** PaddleOCR 계열 mobile/tiny
   - 앱 스토어 바이너리에는 넣지 않고, 첫 OCR 실패·CJK 저신뢰 시 다운로드
   - 용량 목표: tiny ~1.5MB, lite/small ~3.5~8MB대
3. **후처리:** 정규화 → fuzzy match → Top-3 UI
4. **LLM 교정 금지(MVP):** OCR 오타 교정에 클라우드 LLM을 쓰지 않는다. 별칭 사전과 편집거리로 흡수한다.

### 4.2 대상별 기대치 (가설 → 벤치마크 후 확정)
아래 수치는 **출시 전 실측으로 교체**해야 하는 가설이다. 카드 100장 고정 세트로 측정한다.

| 대상 | 조건 | 1차(OS OCR) 가설 | +PP-OCR 보강 가설 | 매칭 후 Top-3 목표 |
| --- | --- | --- | --- | --- |
| 영문 카드명 | 정면, 충분한 조명 | 이름 추출 90~98% | 유사 | **Top-3 ≥ 95%** |
| 한글 카드명 | 정면, 충분한 조명 | 70~85% | 85~95% | **Top-3 ≥ 90%** |
| 일문 카드명 | 정면 | 65~80% | 80~92% | **Top-3 ≥ 88%** |
| 반사/기울기/흐림 | 실사용 평균 | 40~70% | +5~15%p | Top-3 + 수동검색 |
| 인형/피규어(텍스트 없음) | - | OCR 무효 | OCR 무효 | **MVP 제외 또는 Phase 2** |

### 4.3 인식률을 올리는 매칭 전략 (OCR보다 중요)
OCR raw accuracy만으로 MVP를 잡지 않는다. **매칭 계층**이 본체다.

1. 전처리
   - Unicode NFKC, 공백/특수문자 제거, 전각→반각
   - 흔한 OCR 혼동 치환: `0/O`, `1/l/I`, `피카츄/피카추` 등 별칭 테이블
2. 후보 생성
   - `name_ko` / `name_en` / `name_ja` / `aliases[]`에 대해
   - exact → prefix → trigram/편집거리(Levenshtein/Jaro-Winkler)
3. 보조 신호(카드)
   - HP 숫자, 타입 아이콘 근처 텍스트, 세트번호/콜렉터 넘버(가능 시)
4. 실패 UX
   - Top-3 강제 선택
   - 로컬 검색 폴백
   - “다시 찍기” 가이드(반사 줄이기, 카드명 영역 크롭)

### 4.4 벤치마크 계획
- 데이터셋: 실물/스캔 카드 이미지 **최소 100장** (한/영/일 비율 명시)
- 지표:
  - `ocr_name_recall@1`: OCR 문자열이 정답명과 exact/정규화 일치
  - `match_recall@1`, `match_recall@3`: fuzzy 매칭 후
  - latency P50/P95 (기기별)
- 게이트: **한글 카드 `match_recall@3 ≥ 0.90`** 미달 시 PP-OCR 보강 또는 MVP 카드 언어 범위를 축소

## 5. Local Scan Core (병합 안건: Dex 확보 + OCR 매칭)

> DB 없이 OCR만, OCR 없이 DB만 따로 진행하지 않는다.  
> **같은 파이프라인·같은 완료 게이트**로 묶는다.

### 5.0 병합 완료 정의 (Definition of Done)
1. PokéAPI → `dex.sqlite` + `name_aliases` 적재·검증 완료  
2. 동일 DB로 fuzzy matcher가 Top-3를 반환  
3. OS OCR 출력 문자열을 matcher에 넣어 한글 카드 `match_recall@3 ≥ 0.90` (벤치)  
4. 위 과정이 **네트워크/Supabase/서버 인스턴스 없이** 기기(또는 로컬 시뮬)에서 재현

### 5.1 원칙
- **정형 사실 데이터**(이름, 타입, 종족값, 진화 조건, 상성)만 번들한다.
- **공식 스프라이트/카드 이미지/성우 음원**은 라이선스 없는 한 앱에 동봉하지 않는다.
- 모든 행에 `source`, `source_url`, `dataset_version`, `updated_at`을 남긴다.
- 크롤링(나무위키 등)은 ToS/권리 리스크가 커서 **1차 소스로 쓰지 않는다.**
- 런타임에 Supabase/원격 DB를 조회해 매칭하지 않는다.

### 5.2 소스 매트릭스 (권장)

| 데이터 | 1차 소스 | 확보 방법 | 라이선스/주의 | MVP |
| --- | --- | --- | --- | --- |
| 종/폼/타입/능력치/진화 | [PokéAPI](https://pokeapi.co) | REST 또는 공식 데이터 덤프 → SQLite 빌드 | 커뮤니티 API, 이용 시 rate limit·캐시 필수. 게임 팩트 재구성 | 필수 |
| 다국어 이름(한/영/일) | PokéAPI `pokemon-species.names` | API 필드 추출 | 공식 표기 사실 데이터로 취급, 저작권 문구/도감 설명문 장문 복제 금지 | 필수 |
| 타입 상성표 | PokéAPI type endpoint 또는 고정 표 | 18×18 테이블 생성 | 규칙 데이터, 재현 가능 | 필수 |
| OCR 별칭 | 자체 생성 | 공식명 + 흔한 오탈/띄어쓰기/영한번역 변형 | 프로젝트 소유 | 필수 |
| TCG 카드명·세트·번호 | [PokemonTCG/pokemon-tcg-data](https://github.com/PokemonTCG/pokemon-tcg-data) 등 공개 데이터셋 | JSON → `tcg_cards` 인덱스 | 데이터셋 라이선스 준수. **카드 아트 재배포 금지** | Phase 1.5 |
| 최신 세대(미반영 종) | 공식 발표/신뢰 가능한 공개 기사 + 수동 큐레이션 | `manual_stubs` 테이블 | 출처 URL 필수, 미확정 필드 `null` | 부분 |
| 도감 설명 문장 | 자체 작성 짧은 템플릿 | “{name}는 {type} 타입이다” | 공식 도감문 복붙 금지 | 필수 |
| 이미지/보이스 | 사용자 제공 또는 내부 QA 전용 | 기존 `voice_assets` 정책 유지 | 공개 빌드 재배포 금지 원칙 유지 | 기존 정책 |

### 5.3 빌드 파이프라인 (구체)

```text
scripts/build_local_dex/
  1) fetch_pokeapi.py      # species/forms/types/evolution/names 수집, raw 캐시
  2) normalize_dex.py      # pokemon_id/form_id 스키마로 정규화
  3) build_aliases.py      # OCR용 별칭·정규화 키 생성
  4) build_type_chart.py   # 상성표
  5) (optional) import_tcg.py
  6) export_sqlite.py      # app/assets/dex.sqlite + dex.meta.json
  7) validate_dex.py       # 건수/필수 필드/중복/고아 FK 검사
```

산출물:
- `dex.sqlite` (모바일 번들 또는 첫 실행 다운로드)
- `dex.meta.json` (`dataset_version`, `species_count`, `built_at`, `sources[]`)
- 용량 목표(MVP): **텍스트 DB ≤ 15MB** (이미지 제외)

### 5.4 OCR → DB 매칭 데이터 모델 (추가 테이블)

#### `name_aliases`
- `alias_id` (PK)
- `form_id` (FK)
- `locale` (`ko` / `en` / `ja` / `ocr`)
- `alias_text` (원문)
- `alias_norm` (정규화 키, 인덱스)
- `source` (`pokeapi` / `manual` / `tcg`)

#### `tcg_cards` (Phase 1.5)
- `tcg_id`, `form_id`(nullable), `name_printed`, `set_code`, `collector_number`, `locale`, `source`

#### `manual_stubs`
- 미반영 신종: `pokemon_id`(임시), `name_ko/en`, `status=unconfirmed`, `source_url`

### 5.5 매칭 알고리즘 (MVP)
```text
ocr_raw
  → normalize()
  → candidates = lookup(alias_norm exact)
  → if empty: fuzzy(alias_norm, threshold)
  → rerank(locale prior, HP/set hints)
  → return Top-3 (form_id, score)
  → score < τ 이면 수동 검색 UI
```

## 6. 온디바이스 1B 모델 계획
- 용도: intent 분류, 짧은 답변 문장화. **팩트는 DB가 제공.**
- 후보군(추후 벤치로 1개 확정):
  - Llama 3.2 1B Instruct
  - Qwen2.5-0.5B/1.5B Instruct
  - Gemma 2 2B (용량 허용 시)
- 런타임 후보: ExecuTorch / MLC LLM / llama.cpp 계열
- 배포: 앱 본편과 분리 다운로드. 미설치 시 템플릿 응답만으로도 MVP 성립해야 한다.

### 6.0 1B 다운로드 호스팅 (클라우드 스토리지가 필요한가?)

**상시 서버 인스턴스는 필요 없다.** 필요한 것은 “파일 URL에서 받아 기기에 저장”뿐.

| 방식 | 자체 스토리지 | 적합도 | 메모 |
| --- | --- | --- | --- |
| **A. 외부 공개 URL 직링크** (Hugging Face 등) | 불필요 | 실험·초기 PoC | 앱이 HF URL로 다운로드. ToS·가용성·속도는 상대 서비스 의존 |
| **B. Cloudflare R2** (권장 자립형) | R2만 (오브젝트 스토리지) | MVP~배포 | 무료 티어 내 egress/저장 한도 확인. Workers로 서명 URL 가능. **인스턴스 아님** |
| **C. Play Asset Delivery / Feature Module** | Play가 호스팅 | Play 배포 시 | 스토어 경유. 사이드로드·비상업 내부배포와는 별개 |
| **D. APK에 포함** | 불필요 | 비권장 | +수백 MB~GB, 설치 포기율↑ |

권장 단계:
1. **MVP 초기:** 1B 없이 템플릿만 (다운로드 인프라 0)
2. **PoC:** Hugging Face 등 공개 URL 직링크 또는 로컬/USB 사이드로드
3. **배포:** 트래픽·안정성이 필요해지면 **Cloudflare R2**에 양자화 모델 1종 업로드 + HTTPS URL (선택적으로 버전 매니페스트 JSON)

체크리스트:
- Wi‑Fi 권장 / 용량·라이선스 고지 후 동의
- 이어받기, 체크섬(SHA-256), `dataset`/`model_version` 기록
- 실패·용량 부족 시 템플릿 모드 유지
- Dex(`dex.sqlite`)도 같은 R2 버킷에 스냅샷으로 올릴 수 있음 (1B와 동일 패턴)

## 6.1 모바일 클라이언트 트랙 (확정 + 잔여 항목)

Local Scan Core와 **병행**. 클라이언트 스택 확정:
- **Android MVP = Kotlin + Jetpack (확정)**
- **Flutter = iOS 검토 시점에 재논의** (지금 도입하지 않음)
- iOS 네이티브(Swift) vs Flutter는 그때 비교

### A. 카메라 연동
| 항목 | MVP 권장 | 메모 |
| --- | --- | --- |
| API | CameraX (Android) | 권한·수명주기·회전 처리가 단순 |
| 모드 | **스틸 캡처 우선** (셔터 한 장 → OCR) | 실시간 프레임 OCR은 발열·배터리·복잡도↑, Phase 이후 |
| 가이드 UI | 카드명 영역 크롭 프레임 + 반사 주의 문구 | 인식률에 카메라 UX가 OCR 엔진만큼 중요 |
| 해상도 | 과도한 4K 전송 금지, OCR용으로 다운스케일 | 메모리/지연 절감 |
| 권한 | 카메라 필수, 저장소는 최소 | 거부 시 갤러리 이미지 픽커 폴백 |

### B. Android 우선 패키징
| 항목 | MVP 권장 |
| --- | --- |
| 스택 | **Kotlin + Jetpack 확정** (Compose, CameraX, ML Kit, SQLite/Room) |
| minSdk | 26+ 권장 (CameraX / ML Kit 현실 구간) |
| ABI | `arm64-v8a` 우선. 1B/PP-OCR 쓰면 32bit 제외로 용량 절감 |
| `dex.sqlite` | `assets` 번들 또는 첫 실행 다운로드 후 앱 파일 영역 복사 (읽기 전용 오픈) |
| OCR | ML Kit Text Recognition (한/일 스크립트 필요 시 다운로드 모델) |
| 배포 | 내부/사이드로드·Play 내부 테스트 트랙부터. 스토어 심사·IP 고지는 별도 |
| 용량 예산 | 초기 설치 ≤55MB (1B 제외). Dex ≤15MB. 1B는 옵트인 |

### C. 잔여 확정 항목
1. ~~클라이언트 스택~~ → **Kotlin 확정**, Flutter는 iOS 시점에 고민
2. **스캔 UX** — 셔터 확정 유지
3. **APK 용량 예산** — 본편 ≤40MB / Dex ≤15MB / 옵션 별도
4. **저사양 기기 정책** — 1B 미제공 기준(RAM/SoC)
5. **권한·개인정보** — 이미지 로컬 처리, 업로드 기본 OFF
6. **1B 호스팅** — 초기는 생략 또는 HF 직링크 → 배포 시 R2
7. **한글 ML Kit** — 스크립트 팩 다운로드 UX
8. **Play 정책·포켓몬 IP** — 공식 에셋 미포함
9. **테스트 매트릭스** — 중저가 포함 3~5대
10. **iOS** — Android 게이트 후, Flutter 여부 재검토

### D. 모바일과 Local Scan Core 인터페이스 (고정)
```text
Camera/Gallery → JPEG/Bitmap
  → OCR engine (ML Kit…) → raw text
  → shared matcher (동일 알고리즘, Dex aliases)
  → Top-3 UI → 확정 → 로컬 컬렉션/상세
```
- matcher·정규화 로직은 **플랫폼 공유 가능한 순수 로직**(Kotlin multi / 포팅 가능한 스펙)으로 두어 Python 벤치와 결과를 맞춘다.

## 7.5 음성 (온디바이스 제약과의 정렬)
- **핫패스:** Cascaded STT→Rotom/Dex→style TTS (가능하면 온디바이스). 턴제 실시간+barge-in.
- **핫패스 금지:** Moshi / OpenS2S / LLaMA-Omni2 전체 스택을 폰에 상시 탑재.
- **콜드/연구:** 홈 GPU에서 Voice Lab 실험. 상세 `docs/specs/음성_STS_실시간대화_및_Omni2실험_계획.md`.
- “작은 STS”의 실무 해답은 경량 Cascaded이지, 한국어 native 0.5B S2S가 아니다 (Omni2는 실험만).

## 8. MVP 범위 재정의
포함:
1. Local Scan Core: Dex 빌드 + alias + OCR 매칭 (단일 안건)

3. 컬렉션 **기기 로컬** 저장
4. Cascaded 음성 V1 (브라우저/온디바이스 STT+TTS, 독자 보이스)
제외/연기:
1. 유료 OCR/VLM/LLM, 상시 서버 인스턴스
2. 스캔 핫패스에서의 Supabase/원격 DB
3. 인형·피규어 비전, 서버 GraphRAG, AR/3D
4. Supabase 계정 sync (원하면 Phase 이후)
5. Moshi/OpenS2S/Omni2를 제품 기본 엔진으로 사용 (Voice Lab만)
